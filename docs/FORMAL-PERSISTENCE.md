# 正式任务登记与完整计划契约

2026-10-07。正式研究仍未冻结或执行。本次解决技术运行器扩大到正式规模时的登记开销问题，并将已审查的 v0.2 科学设计变成可核对的完整任务契约。使用 codebase-design 整理模块接口，数值内核、历史协议、Windows v1 运行器及其回执不变。

## 问题与改变

Windows v1 技术运行器适合已完成的27主任务/24探测，但每次 `_read` 和 `_save` 都处理累计 JSON 登记。实际 G1/L1/G2 任务绑定的紧凑 JSON 约53,510/55,968/102,979字节，尚未加完整尝试历史。正式50,688任务若沿用该结构，会在每次登记中重新读写不断增长的全部记录。没有以小型51任务成功来替代这一规模问题。

新增 `scripts/completion/task_journal.py` 使用 SQLite 逐任务事务、活动索引和批次索引。任务记录与事件在同一事务提交；源绑定、输出路径和已关闭历史不能被重绑定或截短。正常访问只读取请求任务及已登记的活动任务，完整数据库检查由显式调用执行。`read_task_export()` 可在无原活数据库的目录核对逐任务归档、事件链和身份；这些文件本身不证明进程已退出。

`scripts/windows/formal_owned_runtime.py` 是新的 v2 适配器。原 Job 对象、进程创建、内存观察、失败分类和有限重试代码保留；新增登记源绑定及索引读取。启动前在同一共享主机锁下通过原观察器核对可能遗留的 v1 注册，不能仅凭旧文件或管理进程结束就认为 Job 已结束。新配套费用记录器和原生行为测试已写好，**尚未在 Windows 执行，不算原生验收通过**。此前的 v1 原生验收仍只支持其原版本。

AST 结构核对确认 `run()` 的改变限于索引读取参数和登记模块源绑定；终态文件核验及失败记录识别方法相同。此核对不能替代新增事务/运行器组合在 Windows 上的行为验收。

## 完整正式设计契约

`scripts/completion/formal_study_plan.py` 绑定已接收的开发协议 `f8af8ab024baf0d0c97dc0e2cf52e61c112f57bfa647162204a74adc94ff298b`，只生成既有 v0.2 设计：

- 九目标、256/1024/4096/16384四预算、九工作流，每目标128次四链重复；四批各10,368主任务。
- 每目标每批预选8份原输入，共9,216缓存探测、36,864技术执行调用；选择不读取任务结果，不更换失败配置。
- 1,152份实际输入文件的角色、尺寸和任务映射要求；固定仿射坐标、步长、预热/丢弃、原容差、Picard整段及quasi-DEER逐窗口上限。
- 原36函数、参考类别、L2不可判定事件、整体重复的9,999次BCa重采样、至少20个合格重复及失败/未知时间保留规则。

一项完整计划行为检查覆盖上述任务框架，以及删除任务、重签后放宽精度、擅自开启采样或修改开发步长的拒绝。该检查与六项存储检查分别计数。源 `6aa971a` 生成的 `windows-formal-inference-v1` 计划还完成实际地址检查：23,040个地址/SeedSequence键、4,608个NUTS种子无重复。这是有限集合检查，不证明数学独立，也不替代 Windows 保存的实际随机数组。

计划文件明确 `sampling_allowed=false`、`formal_inputs_generated=false`、`native_environment_frozen=false`。它尚不是可以启动的冻结协议。不能把该 JSON 直接交给旧 `technical_batch.py` 绕过正式入口。
