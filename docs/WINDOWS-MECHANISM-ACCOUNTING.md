# Windows-v1 既有记录的机制核算

2026-10-05｜F2第一部分｜事后描述性分析，不是新的性能测量或因果实验

`scripts/completion/analyze_windows_mechanisms.py`读取原512项任务的实际数组、计时及逐轮记录。每项检查任务身份、结果与数组哈希，复核映射/JVP计数、确认前缀以及两次技术重放的工作量。全部512项计数核对通过。逐任务CSV与分组JSON见`benchmark/analysis/outputs/completion-f2/`。

## 重复计算与确认进度

下表范围是每个执行器16个模型/预算组中位数的最小至最大值；每组4份独立随机数组，保留原配对。转移包括拒绝自环。

| 指标 | quasi-DEER/MALA | Online Picard/RWM |
|---|---:|---:|
| 每输出转移的前向映射数 | 11.906–29.500 | 2.000–6.820 |
| 每输出转移的JVP数 | 5.953–14.750 | 0 |
| 每窗口求解轮数 | 5.953–14.750 | 不适用：滑动窗口 |
| 每轮沿每链平均确认的前缀长度 | 不适用：按完整窗口接受 | 4.493–16.000 |

这些工作量在对应CPU/CUDA任务中一致。quasi-DEER每轮对真实窗口进行一次JVP求值和一次前向残差核验；每输出步的前向计数为两倍平均窗口轮数，JVP另计。Picard每轮执行候选及复核两批映射；确认前缀较短时，为每个最终输出转移重复的映射增加。末端缩短窗口按实际宽度核算。

映射数不是密度/梯度调用数或FLOPs，JVP也不能按一次普通映射的价格相加。当前记录证明存在额外工作，与减速相容；尚不能从这些计数单独确定批处理、JVP、扫描和控制各自造成多少秒成本。

这几个例子用于解释已有记录，并不取代包含全部模型的结果表。A1全拒绝让Picard每轮确认完整窗口，但没有后验移动；G2接受率也很低。不同目标的几何和求值成本同时变化，因此不能仅靠这张表推断“降低接受率会造成某一倍数的加速”。它明确支持下一轮在同一目标内检查调参、确认进度、执行成本与统计误差之间的关系。

## 计时口径与未解问题

首次执行的主机标量等待时间占采样时间的组中位比例：CUDA quasi-DEER约0.97%–4.91%，CUDA Picard约4.48%–6.91%。这些区间只描述已设置的标量计时器；等待中含未完成的设备工作，未包含全部Python循环、张量分配或设备调度。不能把它直接称为全部主机开销，也不能据此证明主机开销不重要。

本次核算不混加首次审计、warmed重放、普通API及R诊断时间。原有完整耗时与独立数组数保持不变，不把技术重放当独立统计重复。

F2仍未完成的部分：在少量固定目标内改变窗口与链数，测量求值/批处理、JVP、扫描与控制的成本及探针扰动，并比较同资源下增加独立链数的路线。先冻结新实验身份，继续保留全部负结果。当前核算不支持新的通用加速、最优窗口或自动配置推荐。
