# 中断恢复与全部尝试成本

2026-10-05。恢复修订及真实工作流核验源码 `d9890b84d918402aedbad9754c93504f9dfc5e09`；最终分析读取修订 `d589678418500a1b1ed2b8a1e46c4d356d51d775`。本工作使用已有TDD与统计审查流程。**这是原生Mac上的有限恢复验证，不是正式实验启动或Windows恢复验收。**

## 恢复规则与已发现问题

`formal_recovery.py` 在原任务之外建立恢复记录，保留原始文件。首先取得相同合作主机锁，再向操作系统检查原工作进程组是否不存在；不依据超时、PID文件或锁文件推断进程结束，不发送终止信号。当前仅接受原生Mac与相同Python、psutil、工作程序、运行器、请求和资源设置。

只有明确分类的基础设施中断才能进入显式重试。重试目的地固定，不能换目录制造多份候选；同一请求再次调用只校验并读取已完成终态。原来的数值／资源失败不能被重试替代。没有进程收据、观察权限不足、工作进程组仍存在或分类含糊时，保持拒绝。

增加检查时发现：管理层终态文件缺失、但工作程序已经报告失败的情况下，最初实现仍可能把它分类为中断。这项人工样例先失败，随后在恢复端和分析读取端均修复。即使恢复记录自身的校验和一致，只要它与工作程序的失败声明冲突，仍须拒绝。早期源码、日志和v1正向样例保留；修订后的真实工作流使用新的 `formal-recovery-companion-mac-v2` 身份，不覆盖v1。

## 实際核验

最终 **7项** 新行为检查通过（4项恢复、3项成本／记录读取），不是将多次重跑累加：

1. 中断后封存，原请求重试，原文件不变；再次调用不执行新任务，篡改证据会被拒绝。
2. 实际终止人工管理进程后，仍活着的工作进程阻止恢复；工作进程组实际结束后才允许分类。缺失的管理层耗时保持未知，未封存输出不自动成为正常样本。
3. 数值或内存保护失败不能改作基础设施中断重试。
4. 工作程序已经报告失败而管理层未封存时，同样不能重试。
5. 多次尝试的成本汇总保留资源失败、已知的部分耗时和原计划分母；未知耗时不补零，共同有效配对里有未知总成本时不计算比值。
6. 从真实终态读取时区分资源失败与原因未分类的输出失败，并检查状态／资产校验和。
7. 分析端拒绝与已知失败声明冲突的恢复记录，不因记录自身有校验和而信任其分类。

人工fixture中的36秒总已知消耗、13秒部分消耗等是手工设定的测试数值，不是实验性能。资源失败单列；只有生产者明确提供原因时才标为数值失败，否则报告 `output_failure_unclassified`。多次尝试仍属于原来的一个完整四链重复，不增加独立n。

## 同一实际MALA输入的恢复

v2伴随核验使用已冻结技术协议中的G1／顺序MALA四链输入。在真实科学工作进程完成轨迹、独立NumPy审计与R诊断后，外层人工注入退出码7，然后按恢复接口重试相同请求。这是预先声明的技术注入，不是新的数值失败或推断实验。

| 核验项 | v2实际结果 |
|---|---:|
| 第一次尝试／重试状态 | interrupted／completed |

| 逐字节相同数组 | draws、unconstrained、accept、primary_accept |

| 原中断尝试已记录耗时 | 2.042050625秒 |

上述时间使用原运行器“准备至终态写入”的边界；不含两个调用之间的恢复分类／封存成本及最终回执自身写入，**不是已经测得的完整普通推断或完整审计成本**。最终读取修订从v2保存证据重算该合计完全一致，没有再采样。

v1和v2各执行两次同一实际输入，共4次技术执行、0个新增独立统计重复。这不证明一般收敛、加速或任意崩溃均可恢复。原58份预算源码与65份运行器技术协议源码保持不变。

## 尚未关闭的门槛

- 当前是显式单任务恢复接口，尚未接入正式调度器的全任务登记、尝试链和成本汇总。全局登记还须阻止其他合作任务在管理进程崩溃后与遗留工作进程重叠；当前同任务的恢复拒绝不能替代这项检查。
- 进程及所有后代必须留在原进程组；没有PID收据、后代脱离进程组、终态已写而最终回执缺失等情况尚无通用自动修复。不能把这些情况强行标为已恢复。
- 原生Windows需要其实际进程集合管理及恢复验收；当前代码明确拒绝在那里使用Mac进程组恢复，不能换用WSL2冒充验证。
- 资源失败与中断成本接口还需接入正式任务格式；参考不确定性、流式分析和三种成本口径不能因为本次检查而降低要求。
- 正式协议冻结、Windows补充／正式数据、两平台干净安装、全论文重建与最终稿仍未完成。
